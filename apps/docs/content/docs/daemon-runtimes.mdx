---
title: Daemon and runtimes
---

Multica calls one deployment model through its API. Install the Multica daemon on each execution computer; external AI coding CLIs and their accounts are no longer required.

The daemon receives runs over the existing authenticated HTTP/WebSocket connection, prepares the work directory and executes native tools. Model inference, summaries, titles and suggestions pass through the API server and share PostgreSQL quotas. API credentials stay on the server.

```bash
multica daemon start
multica daemon status
multica daemon logs -f
multica daemon restart
multica daemon stop
```

Open Runtimes and select the execution computer. Each computer registers Multica Native. Creating an agent uses the deployment model; arbitrary model overrides and CLI profiles are rejected.

File writes and shell commands are disabled by default. Enable `MULTICA_NATIVE_ALLOW_WRITE=true` and `MULTICA_NATIVE_ALLOW_SHELL=true` separately when needed. Shell tools run with the daemon user’s operating system permissions; use a container, VM or dedicated user when isolation is required.

MCP tools support stdio and remote HTTP/SSE under existing permissions. Stdio requires shell permission. Sampling, resources and prompts are not exposed. Native sessions persist model/tool history and checkpoints on the server; skills are loaded through native tools.

Existing run messages, attachments and project directories remain available. External CLI sessions cannot resume as native checkpoints. Migrate bindings after draining active runs and start a new native session; there is no automatic CLI fallback.

If the model is unconfigured, ask the administrator to configure the API server. For connection failures, inspect `multica daemon status` and `multica daemon logs -f`. Restart with `multica daemon restart` after upgrading the daemon.
